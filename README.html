Carbon Audit Control Tower

GHG Protocol Scope 3 · Category 4 Upstream Transportation · 端對端稽核流程操作指南

架構總覽

整條 Pipeline 由三個階段組成，從原始出貨 Excel 到稽核員可查驗的 Control Tower，全程自動化無人工介入：

① 出貨部門 shipping_2024_raw.xlsx · 120 筆運單 · 含設計髒資料（日期格式混用、車種寫法不一、重量單位混合）
② ETL Pipeline Step 2 清洗標準化 → Step 3 路線計算（mock 或 Google Routes API）→ Step 4 DEFRA 2023 碳排計算 + Audit Trail
③ Control Tower carbon_audit_records.json 由 server.js 注入 → localhost:3000 · 互動式查核控制台 · 地圖即時渲染路徑

💡 核心設計：以動態數位軌跡（Polyline + Timestamp）取代靜態截圖存證，符合 ISAE 3410 對數位審計軌跡的要求。

generate_shipping_data.py · 產出 120 筆 2024 年度運單

刻意注入真實髒資料特徵，用於驗證 ETL 清洗健壯性：

出貨日期 4 種格式混用（YYYY/MM/DD、YYYY-MM-DD、MM/DD/YYYY、YYYY.MM.DD）100% · 遺漏 ~7%
車種 6 種不同寫法（含簡體字、英文縮寫）100%
毛重 混合 kg / 噸 / 帶單位文字 ~25% · 遺漏 ~5%
司機自填距離 80% 空白，不可靠 → 凸顯 API 距離的必要性
工作表

出貨明細 / 圖例與欄位說明 / 匯出摘要

etl_clean.py · 清洗標準化 + 品質旗標

日期標準化 嘗試 4 種格式解析 → ISO 8601；失敗 → WARN_DATE
車種標準化 對應表（6 種寫法 → HGV / LGV / LGV-S）；未知 → WARN_VEHICLE
重量標準化 自動識別 kg / 噸 / 文字單位 → 統一 kg；遺漏 → WARN_WEIGHT

車種代碼與品質旗標

vehicleCode 標準代碼

HGV · Heavy Goods Vehicle · > 7.5 t

LGV · Light Goods Vehicle · 3.5–7.5 t

LGV-S · Light Goods Vehicle Small · < 3.5 t

qualityLevel 判定

OK · 所有欄位乾淨，無需修正

WARN · 至少一個欄位被自動修正

ERROR · 無法修正，排除不計入碳排

2024 全年：OK=98 · WARN=22 · ERROR=0

compute_routes.py · 路線計算 orchestrator

讀取 ROUTE_PROVIDER 環境變數，委派給對應的 provider：

ROUTE_PROVIDER=mock（預設）

mock_provider.py

Quadratic Bezier 曲線 · 10–14 點

Haversine × 1.30 道路係數

可離線執行 · routeSource: MOCK_v1

ROUTE_PROVIDER=routes ✅

routes_provider.py

Google Routes API v2 · 1,000–2,000 點

真實公路距離與路網軌跡

需啟用 Routes API · routeSource: ROUTES_API_v2

審計意義

ROUTES_API_v2 的路徑可逐段核對，符合 ISAE 3410 對數位取證的要求；routeSource 欄位記錄在 audit_trail.jsonl，稽核員可查知每筆碳排的路徑資料來源。

calculate_carbon.py · DEFRA 2023 碳排計算

HGV > 7.5t
0.150 kg CO₂e / tonne-km · DEFRA 2023 v1.4
LGV 3.5–7.5t
0.300 kg CO₂e / tonne-km · DEFRA 2023 v1.2
LGV-S < 3.5t
0.467 kg CO₂e / tonne-km · DEFRA 2023 v1.1
計算公式
距離(km) × 載重(tonne) × 排放因子 = 碳排量(kg CO₂e)

Step 1 / 4

audit_trail.jsonl 說明

每行一筆完整的計算快照，格式為 JSON Lines（NDJSON）。稽核員可追溯每筆碳排的完整輸入 → 公式 → 輸出。

{
  "schema_version":  "1.0",
  "waybill":         "TW-2024-00001",
  "vehicle_raw":     "大型貨车",          // 原始髒資料（保留）
  "vehicle_type":    "HGV",              // ETL 標準化後
  "weight_tonne":    8.524,
  "emission_factor": 0.15,
  "ef_version":      "DEFRA 2023 v1.4",
  "co2_kg":          505.05,
  "api_ts":          "2024-05-21T06:01:58Z",   // 路線 API 呼叫時間戳
  "pipeline_run_ts": "2026-04-29T01:56:53Z",   // Pipeline 執行時間
  "routeSource":     "ROUTES_API_v2",
  "quality_level":   "OK"
}

.jsonl vs .json 陣列

.json（陣列）

必須一次載入整個檔案

要修改整個檔案結構才能追加

記憶體壓力大

一個語法錯誤 → 整個檔案失效

.jsonl（每行一筆）✅

可逐行串流讀取

直接 append 一行即可追加

Spark / BigQuery 原生支援

壞掉的行可以跳過，不影響其他

三種使用場景

場景 1 · BigQuery 匯入
場景 2 · 版本比較
場景 3 · 稽核舉證
bq load \
  --source_format=NEWLINE_DELIMITED_JSON \
  --autodetect \
  my_project.carbon_audit.audit_trail_2024 \
  data/output/audit_trail.jsonl

-- 依承運商統計碳排
SELECT carrier, SUM(co2_kg) AS total_co2
FROM `carbon_audit.audit_trail_2024`
GROUP BY carrier ORDER BY total_co2 DESC;

每筆紀錄帶有 pipeline_run_ts 與 ef_version。當 DEFRA 更新排放因子時，重跑 Pipeline 後 append 新批次，即可用同一張 BigQuery 表比較同一批運單在不同版本下的碳排差異。

ef_versionDEFRA 2023 v1.4 → DEFRA 2024 v1.5（更新後）
pipeline_run_ts兩次執行的時間戳自動區分批次
追加方式直接 append 到同一個 .jsonl，無需修改現有資料

ISAE 3410 查核時，直接交付此檔案（或從 BigQuery 匯出 CSV）。每筆紀錄完整保留排放因子版本、原始輸入值與計算過程，pipeline_run_ts 證明數字由自動化產生、非事後手改。

🔒 Anti-tampering：pipeline_run_ts + routeSource 共同證明每筆碳排數據的計算時機與資料來源，滿足數位審計軌跡的舉證要求。

審計軌跡詳情

安全設計

API Key 永遠不出現在任何原始碼或版本歷史中，透過執行時注入機制保護：

.env  →  server.js（執行時注入）  →  瀏覽器（__PIPELINE_DATA__ 同步注入）
.env 已列入 .gitignore，永不進版本控制
audit-control-tower.html 僅含 YOUR_API_KEY 與 __PIPELINE_DATA__ 佔位符，無實際金鑰
server.js 啟動檢查 若 API Key 或 Pipeline 資料缺失，立即報錯退出，不提供殘缺服務

稽核立場說明

「本系統以 API-based 直接取證機制取代傳統截圖存證。保留的 Polyline 數位軌跡與 Timestamp 原始回傳數據，提供更高審計強度與資料可回溯性，符合 ISAE 3410 對數據完整性與自動化控制的要求。」

四項稽核原則

完整性 100% 運單系統化儲存，無人工抽樣，Polyline 完整記錄每趟行程
真實性 Pipeline 全自動計算，無人工干預風險（Anti-tampering），pipeline_run_ts 為證
可回溯性 audit_trail.jsonl 保留排放因子版本、計算時間戳、原始輸入值，可逐筆追溯
標準化 符合 GHG Protocol Scope 3 Activity-based 計算方法，排放因子採 DEFRA 2023
